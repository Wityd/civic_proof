## Architecture and ownership

The React app calls an Express API. The API verifies Supabase Auth tokens, reads
the trusted application role from `public.users`, and accesses Supabase Postgres
and private Storage with a server-only secret/service-role key. Browser code has
no direct access to application tables, Storage objects or wallet signing keys.
The role switcher uses four seeded demo accounts, with no public signup flow.

P2 owns `apps/api`, `packages/shared`, the schema under `supabase/`, authentication,
authorization, invoice transitions, payment orchestration and integration merges.
P3 owns the wallet service and contracts. P4 owns invoice extraction, deterministic
checks and explanations. P5 owns fictional demo content and the delivery module.

## Database conventions

- Primary keys are UUIDs, normally generated by `gen_random_uuid()`.
- Auth-linked `users.id` references `auth.users.id`; use the Auth Admin API to
  create users rather than writing directly to Supabase's managed Auth tables.
- Money uses `bigint` integer cents, with `_cents` column names. Values must be
  nonnegative; invoice amounts and release amounts must be positive.
- Quantities use an exact numeric type, not floating point. Retain submitted
  totals so the rules engine can detect arithmetic mismatches.
- Timestamps use `timestamptz` with `now()` defaults; business dates use `date`.
- SHA-256 values are lowercase 64-character hexadecimal strings. File paths are
  object keys within private buckets, not public URLs or permanent signed URLs.
- `CP001`, `M1` and invoice numbers are human-facing codes, separate from UUIDs.
- Invoice numbers and document hashes are deliberately **not unique**. Duplicate
  submissions must remain storable so P4 can flag them.
- Chain keys are derived from UUIDs by P3. Never use an invoice number as the
  payment idempotency key.
- JSON responses use snake_case fields. API money must be within JavaScript's
  safe integer range before conversion to JSON numbers; reject unsafe input.

Only project-scoped records carry `project_id`; users, suppliers and the reference
catalogue are shared. Child records can resolve their project through the parent.
Ensure a linked milestone belongs to the invoice's project, ideally through a
composite foreign key on `(milestone_id, project_id)`.

Index foreign keys used for joins, the invoice review queue on
`(project_id, status, created_at)`, supplier ownership, `(supplier_id, invoice_number)`,
invoice and evidence SHA-256 lookups, latest AI reviews, and project transactions
ordered by creation time. Avoid cascading deletion of payment/audit records.

## Access and Storage

Enable RLS on every application table. Following the build plan, create no
`anon` or `authenticated` application-table policies. Revoke their direct table
access and grant the backend service role the required access explicitly. Check
existing policies before making changes. RLS does not constrain the service role:
the Express API must enforce roles, ownership and redaction on every request.

Do not add a trigger that copies `user_metadata.role` into trusted roles. Keep
privileged functions inaccessible to browser roles. Use `security_invoker` views
if views are introduced. No Realtime publication or Edge Function is required
for this first setup.

Create these private buckets, preserving any unrelated existing buckets:

| Bucket | Allowed files | Proposed maximum | Access |
| --- | --- | --- | --- |
| `invoices` | `application/pdf` | 10 MiB | Backend only |
| `evidence` | `image/jpeg`, `image/png`, `image/webp` | 10 MiB | Backend only |

Use object keys such as `<project_uuid>/<invoice_or_milestone_uuid>/<file_uuid>.pdf`.
The API validates actual file contents, hashes the bytes and records the object
path. Do not create broad Storage policies for `anon` or `authenticated`.
Authenticated invoice downloads require ownership or staff authorization before
the API returns a short-lived signed URL. Public evidence access, when added,
must use an explicit redaction and publication decision.

## Invoice and payment rules

P3's factory and multichain changes are accepted; see
[P3-INTEGRATION.md](P3-INTEGRATION.md). `FACTORY_ADDRESS` is chain-specific;
per-project addresses are stored in `project_wallets`. The active ledger mode is
`simulated`, `fuji` or `bsc`. Milestones must be registered on the selected project
wallet before linked invoice submission. Registration does not verify delivery.
Hold stays off-chain. P3 still needs to supply actual deployment addresses and
registration receipts; no on-chain addresses or transactions have been invented.

Allowed transitions:

```text
submitted -> analysed -> approved | on_hold | rejected
on_hold -> approved | rejected
approved -> payment_pending -> paid | payment_failed
payment_failed -> payment_pending  (retry)
```

All other transitions return `409 INVALID_STATE`. A supplier sees and submits
only invoices for suppliers assigned to that user. The submitter cannot approve
their own invoice. Hold and reject require a written reason; approving a flagged
invoice also requires a reason and sets `overrode_ai=true`.

Use the detailed shared-contract rule: `PURPOSE_MISMATCH` recommends `REJECT`;
any other high or medium flag recommends `HOLD_FOR_REVIEW`; otherwise `APPROVE`.
The build plan's earlier high-severity-only summary is less specific. P4's checks
must use the detailed rule consistently. Flags: `PURPOSE_MISMATCH`,
`PRICE_ABOVE_BENCHMARK`, `DUPLICATE_INVOICE`, `ARITHMETIC_MISMATCH`,
`BUDGET_EXCEEDED`, `SUPPLIER_REVIEW_REQUIRED`, `NO_BENCHMARK`,
`DUPLICATE_EVIDENCE`.

Payment safety must hold under concurrent requests:

1. Lock the invoice and relevant project funds in one database transaction.
2. Return an existing pending or confirmed release for that invoice.
3. Enforce a partial unique index on `transactions(invoice_id)` for
   `operation='release' AND status IN ('pending','confirmed')`.
4. Check the approved state, available funds and any linked milestone verification;
   reserve funds and insert a pending release atomically.
5. Call P3's wallet service with the invoice UUID as the stable request identity.
6. Mark the release confirmed and invoice paid only after wallet confirmation.
7. Persist unknown chain outcomes for reconciliation; never mark a timeout as
   failed and blindly send another release. Retry only after resolving the result.

The simulated wallet must use the same locking and reservation rules as Fuji.
Compute balance from confirmed funds and releases, and available funds after
approved-but-unpaid reservations. Do not maintain an unlocked balance counter.

Supabase writes and chain calls are not a single atomic transaction. Record each
operation and reconcile partial failures. Invoice registration anchors the file
hash; approval and rejection call the corresponding wallet operations. Holding
does not touch the chain. Official milestone verification also requires confirmed
wallet synchronization before a dependent release is allowed.

## API to implement after setup

Return `{ "data": ... }` or `{ "error": { "code": "...", "message": "..." } }`.
Use 400 for invalid input, 401 for missing/invalid authentication, 403 for denied
access, 404 for missing resources and 409 for state or payment conflicts.

| Routes | Access and behavior |
| --- | --- |
| `GET /health` | Health check; no secrets or connection strings |
| `GET /me` | Signed-in user and trusted role |
| `GET /projects`, `GET /projects/:id` | Public, redacted project records |
| `GET /projects/:id/wallet`, `GET /projects/:id/transactions` | Public balance and ledger with explicit simulated/Fuji mode |
| `POST /projects`, `POST /suppliers` | Municipality |
| `GET /suppliers/:id` | Public supplier profile with contact details removed |
| `POST /invoices` | Supplier; multipart PDF + validated JSON |
| `GET /invoices`, `GET /invoices/:id` | Municipality/auditor, or owning supplier; validate filters |
| `POST /invoices/:id/analyse` | Municipality; call P4, persist validated output |
| `POST /invoices/:id/approve`, `/hold`, `/reject` | Municipality; enforce state, reason and self-approval rules |
| `POST /payments/:invoiceId/execute` | Municipality; idempotent, concurrency-safe payment |
| `POST /milestones/:id/evidence` | Extension: supplier/citizen |
| `POST /milestones/:id/confirm` | Extension: citizen |
| `POST /milestones/:id/verify` | Extension: municipality/auditor; official verification |
| `POST /projects/:id/concerns`, `POST /concerns/:id/respond` | Extension: citizen raises; municipality responds |
| `POST /demo/reset` | Demo-only protected operation; separate reset secret, restricted to demo-owned data |

Public serializers omit user emails, supplier contacts, raw AI prompts, private
Storage paths, signed invoice links and internal errors. Private records use
explicit field allowlists too. Auth verifies the token, then loads the database
role; it never trusts a client-supplied role or a stale metadata role.
